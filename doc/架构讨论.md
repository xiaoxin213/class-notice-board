# 架构讨论：教室端怎么连、能不能连

> 讨论稿 v0.1　　2026-09-07
> 核心议题：教室电脑能不能上外网？纯云端方案是否成立？

---

## 1. 先纠正一个提法：不是"能不能上外网"，是"能不能出站到 443"

原始担心是"教室电脑能不能访问云服务器"。但真正要问的问题更窄：

- ❌ 我们**不需要**教室电脑有公网 IP
- ❌ 我们**不需要**学校给教室电脑做端口映射
- ❌ 我们**不需要**打洞、不需要 P2P
- ✅ 我们只需要教室电脑能**主动向外**建立一条到 `443` 端口的 TLS 连接

这是"反向长连接"模型：教室端主动连云，连接建好后云端沿着这条已有连接把通知推下来。NAT、防火墙对**出站**流量默认是放行的，这一条设计消掉了 90% 的网络难题。

## 2. 中国中小学教室电脑的真实网络状况

**基本面是乐观的。** 现在的班班通/多媒体一体机、教师机日常要用国家中小学智慧教育平台、希沃白板云课件、在线视频资源，绝大多数教室电脑是能上外网的——否则老师的课都上不了。

**但有几类具体障碍要提前设计：**

| 障碍 | 表现 | 应对 |
| --- | --- | --- |
| 上网行为管理（深信服 AC / 锐捷） | 只放行 80/443，封非标端口 | 服务全部走 443，不用 8080/9000 之类 |
| 长连接空闲掐断 | WebSocket 挂 1~5 分钟无数据后被网关断开 | 20~30s 双向心跳 + 指数退避重连 |
| NAT 表老化 | 同上，静默失联，客户端还以为连着 | 心跳 + 服务端 ACK 超时判定离线 |
| Portal / 802.1x 认证 | 开机后未认证就没网，老师上课时才认证 | 客户端要容忍"启动即无网"，持续重试，不要一次失败就躺平 |
| HTTPS 审计（中间人重签证书） | TLS 握手证书不匹配 | Electron 默认走系统证书库，一般能过；Node 侧请求要注意加载系统根证书 |
| 强制代理 | 直连不通，必须走校内代理 | 读系统代理配置（Electron 默认支持），并留手动配置入口 |
| 域名白名单（电子备课室、考场网络较多） | 只有名单内域名能访问 | **域名要单一、固定、已备案**，方便学校 IT 加白 |

**硬件面反而是更硬的约束**：教室机大量是 Win7 32 位 / Win10 LTSC、4G 内存的老机器。这直接决定了客户端技术选型（见 §5）。

## 3. 三个方案

### 方案 A：纯云端（你昨天想的方案）

老师用 Web 页面，教室端 Electron 主动连云服务器 WSS。

- ✅ 零硬件部署，学校侧安装成本 = 装一个 exe
- ✅ 老师在家、在路上都能发（周末临时通知、晚上通知明天带材料，这个场景很值钱）
- ✅ 一套服务覆盖所有学校，升级/修 bug 是服务端的事
- ✅ SaaS 化路径清晰，跑得通就是可复制的生意
- ❌ 强依赖外网：学校断网、统考期间拔网线，产品直接失效
- ❌ 数据出校，若走教委/政采项目会被问合规

### 方案 B：纯校内局域网

每校部署一台服务端（工控机/NAS/或跑在某台常开的办公电脑上），老师和教室端都连校内地址。

- ✅ 不依赖外网，延迟极低，数据不出校
- ❌ 每校一套硬件 + 一次上门部署，**这是最大的成本杀手**
- ❌ 老师离校发不了通知 —— 直接砍掉了最有差异化的场景
- ❌ 校内 IP 变动、设备发现、升级推送，50 所学校就是 50 份运维
- ❌ 浏览器访问校内自签 HTTPS 会一路警告，体验很差

### 方案 C：云优先 + 校内兜底

常态走云；云不可达时切到校内通道。

- ✅ 覆盖了断网场景
- ❌ **现在就做，是过早优化**。两套链路 = 两套状态机 = 两倍 bug，而且"老师和教室是否在同网段"的判断本身就不可靠

## 4. 结论与建议

**第一阶段直接做方案 A（纯云端），但把三件事做扎实：**

1. **全链路 443 WSS**，域名固定单一
2. **降级链**：`WSS(443)` → 失败降 `HTTPS SSE(443)` → 再失败降 `HTTPS 长轮询(2~3s)`。最后这条几乎无法被封——封了它等于封了整个网页浏览
3. **心跳保活 + 断线重连**，重连带指数退避和 jitter，避免网络恢复时全校设备同时冲击服务端

**方案 C 留作第二阶段的条件触发项**：等实测数据证明"确实有成规模的教室机连不上"，再上校内网关盒子。现在不设计。

### 🔧 最该先做的一件事：写一个网络探针

比我们在这里推演一天更有价值的，是拿一个 200 行的探针程序，跑在**几台真实的教室电脑**上，采集：

1. 能否 DNS 解析目标域名（以及走的是哪个 DNS）
2. 能否完成 443 TLS 握手；取证书指纹，判断是否被中间人替换
3. WSS 能否建立；建立后**挂 10 分钟不发心跳**，看多久被掐 → 直接得出心跳间隔
4. 系统版本 / 位数 / 内存 / 是否配置了系统代理
5. 是否存在 Portal 认证（用 204 探测判断）

这份数据是整个架构的地基。找 2~3 所目标学校，跑一周，结论就出来了。

## 5. 配套技术决策

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 教室端框架 | **Electron 22.3.x** | 这是最后一个支持 Win7/8/8.1 的大版本。存量老机器决定了不能用 Tauri（其 WebView2 不支持 Win7） |
| 语音播报 | 云端 TTS 合成 mp3 随通知下发 + 教室端本地 SAPI 兜底 | 云端合成音色统一可控；本地兜底保证网络抖动时也能出声 |
| 进程存活 | 独立守护进程拉起 + 开机自启 + 托盘常驻 | 教室电脑是公共设备，老师会误关 |
| 消息可靠性 | 服务端持久化 + 教室端 ACK（UI 已有"教室端已收到通知"）+ 未达重推 + **TTL** | TTL 很关键：学生都放学了，别还在喊"到操场集合" |
| 绑定码安全 | 6 位数字空间只有 100 万，必须加**尝试频率限制**；绑定成功后下发长期 device token | 否则可枚举，别人能往你教室推通知 |
| 教室端权限 | 只读、无账号、无输入框 | 公共电脑上最小攻击面 |

## 6. 需要你确认的问题

- 目标学校是**自己找的试点校**还是**走教委/集成商**？这直接决定合规压力和方案 B 的必要性
- 教室电脑的操作系统存量分布，有没有大致数字？Win7 占比是关键变量
- 教室电脑是否长期开机？还是老师上课才开？影响"离线通知补发"的产品逻辑

## 7. 决策记录（2026-09-07）

**已定：采用方案 A 纯云端。**

| 决策项 | 结论 |
| --- | --- |
| 整体架构 | 纯云端。教师端与教室端均直连云服务器 |
| 教师端形态 | 一套响应式 Web，同时覆盖 PC 浏览器与手机 H5，不做原生 App |
| 教室端形态 | Electron 客户端，直连云端 |
| 服务端地址 | **可配置**（域名或 IP:端口），不硬编码。便于私有化部署、切换环境、以及学校单独指定接入点 |
| 断网兜底 | 暂缓。方向是"云端 → 班主任电脑 → 局域网分发到教室"，待拿到真实网络数据后再评估 |
| 网络探针 | 暂缓。教室电脑配置暂不可得，改为在首批试点校实装时顺带采集 |

### 关于教师端"一套 Web 覆盖 PC + H5"

方向没问题，但要**移动优先**来设计。老师发通知的高频场景是"课间站在走廊上掏出手机发一句"，而不是"回办公室打开电脑"。现在截图里的三栏工作台（班级列表 / 发布 / 教室绑定）在手机上必须重排——建议手机端只保留"选班级 + 选模板/输内容 + 发布"这一条主干，班级管理和教室绑定收进二级页面。这两个是低频配置动作，本来也更适合在电脑上做。

### 关于"班主任电脑中转"这个兜底方案

同意放到后面。但先把风险记下来，免得将来当成理所当然的退路：

1. **班主任电脑不一定开着** —— 老师大量用手机发通知，人可能根本不在办公室，中转节点就不在线
2. **不一定同网段** —— 办公室和教室常在不同 VLAN，校园网做了隔离的话，办公电脑也推不到教室
3. **它没解决根因** —— 如果学校是整网出口受限，班主任的电脑同样连不上云端

更现实的兜底其实是另外两个方向：在教室侧选一台能上网的机器做中转网关，或者放一个小盒子做校内服务端。等真实数据出来再定，现在不展开。
